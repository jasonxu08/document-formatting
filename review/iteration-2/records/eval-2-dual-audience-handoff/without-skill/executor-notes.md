# Notes on the handoff document (report.md)

## 1. Structure choices and why

- **One file, two parts.** Part A is for Dana and stops after four short sections: bottom line with a status figure, what is needed from her, key dates, and detail on the two real decisions. Part B is for the agent: ground rules, orientation, task cards, evidence, gaps, logs. Dana can stop at the end of Part A; the agent reads both. One file because you asked for "this same document".
- **Led with the ask, not the history.** Dana's two questions are "where do things stand" and "what do I decide". A1 answers the first in five bullets and one figure. A2 is a table with one row per ask (what, Alex's view, by when). The option detail for Q1 and Q2 sits below the dates, so the table stays skimmable. The daily work log is not reproduced; everything is reorganised by task and by decision.
- **Kept your IDs.** T1-T11 and Q1-Q6 are unchanged, so every reference lines up with your notes. I added Q7 (who the agent escalates to), because the agent cannot attend the DBA window or approve production steps and Dana is the obvious person.
- **One figure.** The main message is a gating structure: four things (Q1-Q4) hold up the rollout, which holds up decommissioning. A status and dependency map shows that faster than prose. It has alt text, a caption saying it is a snapshot, and its Graphviz source (`assets/task-status.dot`). The table in B3 carries the same information as text for the agent and is the live version.
- **Task cards for the agent.** Every remaining task has State, what you can do now, what needs a human, and Done when. The "if Dana decides X, do Y" mapping lives inside the cards (T5 for Q1, T6 for Q2) so each task has one place to look.
- **Rules before tasks.** B1 lists what needs a recorded human go-ahead (production migration, production flag changes, worker count, cron changes, customer communication) and what must never happen (copying secrets, retrying dead ends). The rules follow from your notes, but the full list is my wording.
- **"Not in the notes" table.** Each gap has a "how to find out" (read the repo, or ask Dana), so the agent can proceed or escalate instead of stalling or guessing.
- **Decision log and Update log at the end.** Answers and progress flow back into the same document. The agent treats a decision as final only once it is logged, and escalates with a `NEEDS DANA:` row.
- **Tags.** Everything beyond your notes is tagged **[Assumption]** (an ambiguous reading I chose) or **[Suggestion]** (an idea you have not seen). Untagged statements are your facts or calendar arithmetic. Checklists and ordering are new by nature.
- **Dates** are ISO with the weekday where it matters (DBA windows are Tue/Thu). I computed the weekdays rather than trusting memory.

Stated as an assumption under the A2 table. I did not claim a "last DBA window that fits", because that depends on build and rollout time, which the notes do not give.
- **"Cutover".** I assumed it means all tenants running on JobRunner (T9 finished), with T10 later and undated.
- **Who decides Q2 (budget), and who the agent escalates to.** Assumed Dana; flagged. Also assumed that staging work is in scope for the agent and that production changes need a human go-ahead. None of this is in your notes.

The 21-minute run does not say dataset sizes or whether it is the slowest export or the average. The "212 pass, 1 xfail" on 10-05 refers to an xfail added on 10-08. I flagged all three and did not try to resolve them. The "6 workers would fix it" claim has no recorded test, so the document calls it an expectation.
- **Things the notes imply but do not say.** Whether the 11 "mapped" cron jobs exist as separate YAML definitions (only `export-dataset.yaml` is mentioned). How legacy cron and JobRunner avoid both running a migrated tenant's exports. Which branch holds your work and whether it is pushed. What "CET" means given daylight saving (EU clocks change on 2026-10-25, during your leave). All listed in B5 or the cards, with how to resolve them.
- **My extras.** The staging 6-worker test, the XLS timing spike, observability before rollout, the stage checks in the T9 runbook, and a 2026-10-30 status note to Dana are mine. They are tagged; delete any you disagree with.
- **Length.** About 4,600 words in total; Part A is about 1,300 with tables and alt text. I kept Part B detailed because the agent cannot ask you. It could be trimmed if you prefer a shorter document.
- **Rendering.** I converted the Markdown to HTML and checked it in headless Chrome (tables, figure, code block all fine; the figure text is small at narrow widths). I could not check GitHub or an Azure DevOps wiki, where column wrapping may differ.
- **Housekeeping.** One browser-tool call wrote two scratch files into the starting repository's `.playwright-mcp` folder (it did not exist before); I deleted them. I also ran a temporary local preview server on 127.0.0.1:8765 and stopped it. Nothing else outside the outputs folder was touched, and the scratch files in the outputs folder are removed.
